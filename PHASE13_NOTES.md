# Phase 13 notes — Mobile: unified reports screen

Companion to [`../Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 13. Mobile-only — no backend changes were needed (Phase 5's report endpoints already accept the EMPLOYEES role and self-scope correctly; the gap was entirely that this app never called them).

## The product decision, and what I found before asking

The plan explicitly flags naming/IA as "requires a product/design decision — flag explicitly rather than guessing in engineering," so I investigated what actually exists before asking, rather than asking blind:

- Home screen has a chart toggle literally labeled **"Report"** (`AppString.report`) showing working-hours/break-hours charts — nothing to do with documents.
- Profile → **"Pay Role"** lists real, company-uploaded payroll PDFs (view/download/open-externally) — this one is accurately named for what it does, just narrowly payroll-only.
- The real timesheet/attendance report endpoints were never called from this app at all.
- Structurally, the new reports fetch differently from existing payroll PDFs: payroll files are pre-hosted URLs (`SfPdfViewer.network`); the new reports return PDF/Excel bytes directly from an authenticated call (`SfPdfViewer.memory` after a manual `http` GET with the bearer token, the same pattern `PayroleScreenController.downloadPdf` already uses for raw bytes).

Presented this with two concrete options; the user chose: **keep Pay Role payroll-only, add a new separate "Reports" section, and rename the Home chart toggle** to stop it colliding in meaning with the real reports feature.

## What was built

- **`lib/screens/reports_screen/`** (new) — `ReportsScreen` (toggle between Timesheet/Attendance, month dropdown or start/end date pickers depending on type, format/language dropdowns, Generate button, result panel with View/Download/Share), `ReportsScreenController` (fetch orchestration + PDF-viewer-adjacent state), `ReportPdfViewerScreen` (`SfPdfViewer.memory` variant of the existing `PdfViewerScreen`, needed because these reports arrive as bytes, not a URL).
- **`ReportRepository`** — added `fetchMonthlyReport`/`fetchAttendanceReport`, both raw `http` GETs with the bearer token attached manually (same reasoning as the existing payroll download code: binary responses don't fit `ApiServices`' JSON-oriented methods). Always self-scoped — no `employee` query param sent, since the backend ignores it for the EMPLOYEES role regardless.
- **Native share sheet** (`share_plus`, new dependency) — `shareReport()` writes the generated bytes to a temp file and hands it to `SharePlus.instance.share(ShareParams(files: [...]))`, the actual missing capability the plan's audit flagged (previously download-to-disk + open-externally only).
- **Profile nav entry** ("Reports", reusing the existing `pdfIcons` asset — no new icon needed) and route, alongside (not replacing) the existing Pay Role entry.
- **Home screen's "Report" chart toggle renamed to "Overview"** — the only other place `AppString.report` was used (confirmed via a full-codebase grep before touching it), so this was a safe, contained rename.
- Full localization: every new string added to all four languages this app supports, matching the established convention.

## Two things worth being precise about, not just claiming "done"

**The async/slow-report edge case doesn't actually apply to this app, and I'm not pretending it does.** The plan's edge case list assumes a report might "take noticeably long (large range, Phase 5's async path)." I checked: Phase 5/8's async job endpoint (`POST /reports/attendance/async`) is scoped to `COMPANY`/`ADMIN`/`SUPER_ADMIN` only — an `EMPLOYEES`-role caller (this app's only user) always gets the synchronous, always-self-scoped path (`generateAttendanceReportData`'s first branch is unconditional self-only for that role), which is inherently small — one person, at most a year of days. There is no scenario where a mobile user's own report is large enough to need async handling. No async UI was built, and no Phase 3 "report ready" push wiring was needed, because the situation those would exist for cannot occur for this role. This is a scope clarification, not a shortcut.

**The zero-data edge case is already handled — by the backend, not by new mobile code.** I checked before building anything special for it: `timetracker.attendance.test.ts` proves the backend renders "a clean all-absent report... (no crash, no 500)" for zero attendance data — a real, valid, if sparse, PDF/Excel, never an empty response. So the correct mobile behavior is simply the normal success path (view/download/share the sparse-but-valid document), which the code already does. A defensive `ReportGenerationState.empty` branch does exist in `ReportsScreenController` for a genuinely empty response body, but given the backend's actual behavior this is a fallback for a scenario that shouldn't occur in practice, not the real "zero-data" case the plan describes — worth being clear about rather than claiming a dedicated empty-state UI was needed to solve something the backend already solved.
