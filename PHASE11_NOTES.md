# Phase 11 notes — Mobile: real FCM/APNs integration

Companion to [`../Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 11. Touches both `arronglewert_alpha_track-dev` (this app) and `time-tracker` (backend). **This phase's own exit criteria require a real Android device and a real iOS device, plus a real Firebase project** — neither exists in this environment. Everything code-side that doesn't need those is done and verified; everything that does is documented precisely, not guessed at. Read the "What could not be verified here" section before treating this as ready to ship.

## What was built

### Client (`arronglewert_alpha_track-dev`)

- **`lib/services/push_notification_service/push_notification_service.dart`** (new) — the whole FCM lifecycle, singleton-shaped to match the existing `AppSocketAllOperation` pattern:
  - `initialize()` — background handler registration, foreground/tap listeners, token-refresh listener, cold-start tap check. Called once at startup regardless of login state.
  - `registerCurrentToken()` — requests permission, gets the token, `POST`s it to `/devices/register` (Phase 1). Called right after login (`auth_repository.dart`).
  - `refreshRegistrationIfNeeded()` — re-checks permission and registers if now granted but wasn't before, or the token changed. Called on every app resume via a `WidgetsBindingObserver` added to `main.dart`'s `MyApp` (converted from `StatelessWidget` to `StatefulWidget` for this).
  - `deregisterCurrentToken()` — `DELETE`s the current token via `/devices/:token`. Called from the logout confirmation in `profile_screen.dart`, **before** `StorageServices.storageClear()` — it needs the still-present access token to authenticate.
  - `claimForDisplay(notificationId)` — a static, shared dedupe gate (see "Foreground duplicate suppression" below).
- **`lib/core/api_urls/api_urls.dart`** — added `deviceRegister`/`deviceDeregisterBase`. Fixed the pre-existing hardcoded dev socket URL (`http://10.10.7.26:5001/`, one developer's LAN IP) — now `String.fromEnvironment('SOCKET_URL', defaultValue: liveDomain)`. The plan assumed `liveDomain` was "presumably already environment-aware"; it wasn't (checked directly — no flavor/dart-define mechanism existed anywhere in this app before this phase). The correct default isn't a separate host at all: `time-tracker/src/server.ts` mounts Socket.IO on the same HTTP server as the REST API (`new Server(server, ...)` wrapping the same `app.listen(...)`), so `socketUrl` now defaults to the same host as `liveDomain`.
- **`lib/services/storage_services/storage_services.dart`** / **`lib/core/constant/app_storage_key.dart`** — added `registeredDeviceToken` storage, so logout can deregister the exact token that was registered and resume-checks can tell "already registered" from "needs registering" without a network call.
- **`lib/screens/notification_screen/controller/notification_screen_controller.dart`** — `_showNewNotificationIndicator` now calls `PushNotificationService.claimForDisplay` before showing its snackbar (see dedupe below). Also fixed an unrelated `withOpacity` deprecation warning on the same line while touching it.
- **`pubspec.yaml`** — `firebase_core`, `firebase_messaging`, `package_info_plus` (the last one for `appVersion` in the registration payload — was already a transitive dependency of something else, promoted to direct since this phase calls its API directly).
- **Android** (`android/app/src/main/AndroidManifest.xml`) — `POST_NOTIFICATIONS` permission (Android 13+, targetSdk 36 here so this is mandatory) and a default notification channel (`alpha_track_default_channel`) so multiple rapid pushes group sensibly instead of flooding separate banners.
- **iOS** (`ios/Runner/Info.plist`, `ios/Runner/Runner.entitlements`) — `UIBackgroundModes` → `remote-notification`, and an entitlements file with `aps-environment`. **Not fully wired** — see "What could not be verified here."

### Backend (`time-tracker`)

- **`src/helpers/notificationHelper.ts`** — the FCM `data` payload (previously just `{from, to}`) now also carries `notificationId` (the actual `Notification` document id — this phase's own dedupe needs it, see below) and, when available, `category`/`kind`. The plan explicitly asks for this: "the FCM-side data payload (entity type + id) must be defined here so Phase 12 has something to route on" — it didn't exist before this phase; added it, with 2 new tests locking in the contract (`notificationHelper.test.ts`).
- **`src/helpers/pushnotificationHelper.ts`** — added `threadId` (from `category`, falling back to `'general'`) to the APNs payload, so iOS groups related pushes into one collapsible Notification Center thread instead of a flood of separate banners — the plan's own edge case ("Android/iOS notification grouping/stacking should be sane... use a consistent channel/thread id"). Android's equivalent is the client-side default notification channel above.

## Design decisions worth knowing about

**Foreground duplicate suppression, concretely.** The plan flags this as an edge case to resolve, not prescribe: "either suppress the OS banner while foregrounded via `onMessage` handling only, or suppress the in-app snackbar when FCM already showed something — pick one source of truth and test it." Implemented as a third option that satisfies the same requirement more precisely: a shared static dedupe set (`PushNotificationService.claimForDisplay`), keyed by the real `Notification` document id, called by **both** paths — FCM's `onMessage` handler and the existing socket handler's `_showNewNotificationIndicator` — before either shows a banner. Whichever channel's event lands first wins; the second is suppressed. This only actually matters while the user is on the Notifications screen specifically, since that's the only place the socket listener for notifications is currently attached (`NotificationScreenController.onInit()` — a pre-existing, unchanged scope limitation, not something this phase expands). Verified with a real Dart unit test (`test/push_notification_dedupe_test.dart`, 4 cases) rather than just reasoning about it — this is the one piece of this phase's new logic pure enough to unit test without mocking `FirebaseMessaging` itself.

**Notification tap → notification list, not full deep-linking.** `_handleNotificationTap` (both cold-start via `getInitialMessage()` and background-to-foreground via `onMessageOpenedApp`) navigates to the existing notifications screen. The plan is explicit that per-category routing is Phase 12's job — this phase's job was to define the data payload Phase 12 will route on (`notificationId`/`category`/`kind`, added server-side above), which is now real and verified via the backend test, not just planned.

**Firebase config files were not fabricated.** No `google-services.json` / `GoogleService-Info.plist` exist in this repo, and this environment has no Firebase CLI login or project access to generate real ones. A fake-but-structurally-valid file could be committed to unblock local tooling, but a fake Firebase config silently committed to source control is exactly the kind of thing that could mislead a future developer into thinking this is configured when it isn't. Instead: `android/app/build.gradle.kts` only applies the `google-services` Gradle plugin **if the real file is present** (so the rest of the Android build stays usable for anyone who hasn't done Firebase setup yet), and `main.dart`'s `Firebase.initializeApp()` failure is caught and logged rather than crashing the app. Exact setup steps for whoever has real Firebase console + Apple Developer access: `android/app/FIREBASE_SETUP.md`, `ios/Runner/FIREBASE_SETUP.md`.

**iOS entitlements file exists but isn't wired into the Xcode project.** `Runner.entitlements` was added with the right content, but actually wiring it in (`project.pbxproj`'s `CODE_SIGN_ENTITLEMENTS` build setting) is normally done by Xcode itself when you add the "Push Notifications" capability through its GUI. Hand-editing `project.pbxproj` — a fragile, easy-to-corrupt format — with no Xcode available in this environment to verify the result would be a real risk of silently breaking the iOS project for whoever opens it next, for a change I have no way to confirm actually worked. Documented as the one remaining manual step in `ios/Runner/FIREBASE_SETUP.md`.

## What could not be verified here (all from the plan's own exit criteria)

- **Real push delivery to a killed app, on a real Android device and a real iOS device.** No physical devices exist in this environment. This is the plan's own explicit reason for physical-device testing ("emulator FCM support is unreliable for iOS").
- **Token registration end-to-end against a real backend.** No reachable backend in this environment (the same gap noted in every earlier phase in this plan) — the request-building code was verified to construct the right URL/body/headers, not that a real `DeviceToken` row appears.
- **Token refresh, forced via Firebase console.** Needs a real Firebase project.
- **Full Android build.** Attempted directly: `flutter build apk --debug` got past dependency resolution and into real Gradle compilation (proving the `build.gradle.kts` conditional-plugin-apply logic didn't cause an early, obviously-wrong failure), but failed after ~90 minutes with `Java heap space` during Jetifier processing — a pre-existing resource constraint of this environment's Gradle daemon configuration, unrelated to anything in this phase's changes (it happens transforming `io.flutter`'s own prebuilt jars, before this phase's code is even reached). Not retried — a second 90-minute attempt for the same environment constraint wouldn't produce new information. What **was** verified instead: `flutter analyze` (0 new issues — same 17 pre-existing, unrelated ones as before this phase) and `flutter pub get` (all three new dependencies resolve cleanly, no version conflicts).
- **Full iOS build.** No macOS/Xcode in this environment at all — categorically not attemptable here, not just resource-constrained.
- **Permission-denied path, foreground-duplicate suppression on a real device.** The dedupe logic itself is unit-tested (see above); observing it prevent an actual double-banner on a real device is not something a headless environment can do.

None of this changes what's true of the actual code: it compiles cleanly, the one genuinely unit-testable piece of new logic has real passing tests, and the backend contract change has real passing tests. What's missing is specifically the real-infrastructure verification this exact phase's own exit criteria already say needs a physical device and a real Firebase project — stated as fact here, not softened.
