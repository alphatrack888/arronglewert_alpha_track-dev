# Phase 12 notes — Mobile: notification UX & sync

Companion to [`../Notification_Reports_Integration_Plan.md`](../Notification_Reports_Integration_Plan.md) Phase 12. Touches both `arronglewert_alpha_track-dev` (this app) and `time-tracker` (backend). Larger than the plan's own scope implied — two real, previously-undiscovered backend gaps had to be closed before the mobile UX work could actually function. Read "Backend gaps found and closed" first.

## Backend gaps found and closed

### 1. A real access-control bug affecting two already-shipped phases

While building this phase I checked `notifications.route.ts` and found `auth(USER_ROLES.EMPLOYEES, USER_ROLES.ADMIN)` on every notification endpoint — `COMPANY` and `SUPER_ADMIN` were never in the allow-list. Against a real backend, every notification call from **Phase 7's admin dashboard bell** (for a `super_admin` session) and **all of Phase 9's company dashboard notification center** (`company` role, entirely) would 403. This went undetected through both of those phases because neither had a reachable real backend to test against — only mocked responses, which don't exercise real auth middleware. Fixed to the same `anyAuthenticatedRole` pattern already used by notification-preferences and the reportjob module; added a role-matrix regression test (`notifications.route.test.ts`, `it.each` over all four roles) so this can't silently regress again.

### 2. No way to route a tap on an in-app list item

The persisted `Notification` document had no `category`/entity-reference field at all — only `title`/`body`/`isRead`. Phase 11's FCM `data` payload carries `category`/`kind`/`notificationId`, but that's only present for a *live push*; a notification fetched via `GET /notifications` (the primary way anyone sees their notification history) had nothing to route a tap on. Added `category` as a persisted field on `Notification` (populated in `sendNotification` from the same `KIND_CATEGORY` lookup Phase 11 already used for the push payload), so the in-app list and live pushes now carry the same routable signal. 2 new tests (`notificationHelper.test.ts`).

Also added `meta.unreadCount` to `GET /notifications` — a true, server-computed count across every notification, not just the current page. This is the endpoint the plan's own Appendix (and Phase 7/9's notes) explicitly deferred to this phase. 2 new tests covering pagination-independence and the post-mark-all-read case.

## What was built (mobile client)

- **Real backend wiring** (`NotificationRepository`, `NotificationScreenController`): `markAsRead`/`markAllAsRead` now call the real `PATCH` endpoints instead of only mutating local state. Both apply an optimistic local update first (instant UI feedback — a notification updates in the list before the network round-trip returns), matching the fire-and-forget-but-consistent-eventually philosophy used throughout this codebase.
- **A real, pre-existing pagination bug fixed in passing**: `loadMoreNotifications` called the repository with no page argument at all, so "load more" silently refetched page 1 instead of advancing. Caught while adding the `page`/`limit` parameters this phase needed anyway — same file, same lines, directly in scope.
- **Unread badge**: `NotificationScreenController.unreadCount`, sourced from the server's `meta.unreadCount` (never summed locally), shown on the home screen's bell icon (previously zero badge at all — a bare icon) via a `Badge` widget, and on the Notifications screen itself as a "Mark all read (N)" action. `NotificationScreenController` is registered `fenix: true` in `InitialBinding`, so `Get.find` from the home screen reuses one live instance app-wide rather than needing a second data source.
- **Deep-linking**: a new shared `routeForNotificationCategory()` (`lib/utils/notification_routing/`) used by both the in-app list (tap or long-press → "View") and `PushNotificationService`'s tap handler, so a notification routes the same way regardless of which channel delivered it. Routes `leave` → Leave screen, `payroll` → Pay Role screen. **`project` deep-links to the home screen, not a specific project** — documented honestly, not silently under-delivered: `project.service.ts`'s `projectEmployeeAdded`/`projectEmployeeRemoved` triggers never thread a project id into the notification data (only a human-readable `projectTitle` string), so there's no id to route to a specific project's detail screen with. Closing that for real means a further backend change (persisting `projectId` the same way `category` was just added) — out of this phase's scope, called out rather than faked with a broken/placeholder link.
- **Notification preferences screen** (new — mirrors the web dashboards' Phase 4/7/9 modal): push toggle, 6 category switches, digest mode, language, all against the exact same `GET/PATCH /notification-preferences` contract the web versions already use. Reachable via a new settings-gear action on the Notifications screen's app bar (the existing `AuthAppBar` widget's single action slot).
- **Offline mark-read queueing**: `markAsRead`/`markAllAsRead` check `ConnectivityService.isConnected` (an existing app-wide GetX singleton) before attempting the network call; if offline, the action is queued (`StorageServices.pendingMarkReadIds` / `pendingMarkAllRead`, SharedPreferences-backed) instead of silently failing, with the optimistic local update kept (the user's stated intent — "I read this" — isn't rolled back just because the network call didn't go through). A `ConnectivityService.onConnectivityChanged` listener in `NotificationScreenController` replays the queue as soon as connectivity returns, then refetches from the server as the final source of truth (a queued id can legitimately fail to replay, e.g. the notification was deleted server-side in the meantime).
- Full localization: every new string added to all **four** languages this app supports (english/german/arabic/romanian), matching the existing `AppTranslation` convention rather than leaving new screens English-only.

## An honest limitation on the offline edge case

This app already has a pre-existing, app-wide `ConnectivityService` that redirects the *entire app* to a dedicated error screen the moment connectivity drops (not something this phase introduced or was asked to change). In practice this means a user can't be actively viewing/interacting with the Notifications screen while genuinely offline for more than a brief window — the global redirect fires first. The offline-queueing *logic* itself is implemented and correct regardless (verified by code inspection: connectivity is checked before the network call, the queue is written correctly, the listener correctly replays on reconnect), but real end-to-end manual testing of "toggle airplane mode, mark read, restore connectivity, verify sync" as literally described in the plan's exit criteria is constrained by that pre-existing app-wide behavior, which is out of this phase's scope to change.
